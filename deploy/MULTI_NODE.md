# XIASS 多节点执行与入口负载均衡

XIASS 多节点模式让多个对等应用实例共同连接同一套 PostgreSQL 和 Redis 状态层。客户可继续使用同一个 Base URL 和 API Key；在共享状态可用时，任一 XIASS 应用节点都能完成鉴权、调度、扣费和记录写入，余额、分组、并发、粘性、计费与使用记录以同一份共享状态为准。

**当前不提供内置整机自动容灾。** 多节点执行、网页配对和入口负载均衡不会创建数据库副本、提升数据库主节点、进行仲裁或切换公网 DNS；共享状态所在主机失效时，增加应用节点不能自动恢复服务。

这里有两个必须分开的概念：

- **入口节点**：客户的 HTTP 请求实际先到哪一台 XIASS 服务器，由公网 DNS/边缘入口的 origin 健康检查和权重决定。
- **账号所属节点/上游出口**：调度器最终选中的账号归属哪一台服务器，以及 XIASS 联系上游时使用哪一个固定出口。它由账号的节点归属和共享节点出口映射决定，与入口节点不是一回事。

因此，`api2` 收到一个使用主域名 Base URL 的请求时，可以从共享账号池选中 `api` 所属账号；该请求仍通过 `api` 账号绑定的 `api` 上游出口访问提供商，不会把这个账号的上游流量改从 `api2` 发出。账号归属节点的出口不可用时，按既有故障转移规则选择另一个健康账号，并使用该账号自己的固定出口；没有可用账号时返回失败，不临时改写原账号的出口。

## 链路

```text
客户 -> 带健康检查的外部入口 -> 任一对等 XIASS 实例 -> 共享账号调度 -> 账号所属节点的固定上游出口 -> 上游
```

- 入口负载均衡负责分担公网连接和响应带宽。
- XIASS 节点权重只决定新会话在当前最高账号优先级内使用哪个账号归属节点；它不替代公网入口的 origin 权重。
- `api2` 没有本地账号时仍可作为健康入口，应用会从共享账号池选择 `api` 节点账号；账号仍通过其绑定的 `api` 出口执行。入口健康检查不会因为本节点账号数为 0 而摘除该节点。
- 账号优先级仍是硬顺序；低优先级账号不能凭节点权重越级。
- 普通粘性会话和不可迁移的 `previous_response_id` 链继续使用原账号。
- 节点账号权重设为 `0` 后，该节点归属账号不再接收新会话，但不会中断已有粘性会话；该应用实例仍可作为健康入口，把新请求调度到其他正权重节点的账号。
- 每个账号持久保存归属节点和代理 ID，HTTP、SSE、WebSocket、图片、OAuth 刷新、额度查询和后台探测都使用该账号的固定出口。即使客户请求由另一台 XIASS 实例接入，也只会使用该账号绑定的出口。
- 节点心跳只提供节点可用性信息，不授权其他节点接管该节点账号的出口。重试选择其他健康账号时，仍须遵守账号优先级、固定出口和不可迁移会话链约束；不改写原账号的归属、代理、凭据或计费数据。
- PostgreSQL 或 Redis 若只运行在某一应用机上，该机器断联时其他应用节点也会失去共享状态，不能继续完整服务。状态层的部署、备份和恢复由运维独立负责；本功能不自动复制或提升状态服务。

## 前置条件

1. 所有节点必须运行同一个 XIASS 版本。
2. 所有节点必须连接同一套 PostgreSQL 与 Redis；JWT、TOTP 加密密钥和其他应用密钥也必须一致。必须明确状态服务所在主机及故障影响，不能把应用配对当作状态冗余。
3. 节点之间使用 WireGuard 等低延迟私网互通，不要把 PostgreSQL、Redis 或私网 SOCKS 暴露到公网。
4. 每个执行节点在共享数据库中有一个仅私网可达的 SOCKS5 代理记录；代理记录不能被两个节点共用。
5. 先完成隔离测试，再接入带健康检查的 DNS 或边缘负载均衡。应用内账号权重不能代替公网入口负载均衡。

## 对等节点与任务领导者

两个 XIASS 实例在 HTTP 能力上完全对等：

- 数据面：`/v1`、`/v1beta`、Responses、Codex、图片和视频等模型调用路径，按入口权重在多个健康 XIASS 实例间负载均衡。
- 网页与管理端：首页、用户中心、管理 API、Team、OAuth 和上传可由任一健康 XIASS 实例提供。入口使用带健康回退的粘性 Cookie，让同一浏览器流程尽量留在一个实例；该实例断联后自动切换到另一个健康实例。
- `control_plane` 只决定哪一个实例启动无需重复运行的后台周期任务，不限制该实例可接收的 HTTP 路由，也不代表主站、唯一管理端或唯一计费节点。客户鉴权、余额扣减、使用记录、请求时 Token 刷新和调度缓存同步仍由所有网关实例通过共享状态层共同完成。
- 账号/代理到期扫描、定时测试、定时备份、渠道监控、主动 Token/额度维护等周期任务只在 `control_plane=true` 的实例运行。备份计划和渠道监控从任一对等管理面保存后，控制面会在 5 秒内从共享数据库对账，因此不要求管理员固定登录某一个域名。

数据面入口选中哪个应用实例，与最终选中哪个账号是两件独立的事。应用实例从共享账号池调度后，仍按账号持久化的节点归属和私网 SOCKS 走固定出口。因此 `api2` 接收的请求可以使用 `api` 账号，但该账号仍从 `api` 公网出口访问上游；反向亦然。

## 公网入口

应用内的“多节点执行负载均衡”只负责从共享账号池选择执行账号，并验证账号与固定出口的绑定；它不会改变客户请求到达哪一台服务器，也不会自动修改公网域名的 DNS。要分担客户主域名的公网连接和响应带宽，需要在已有的边缘入口上配置两个 HTTPS origin：

- `api` origin：现有节点服务器的 443 端口。
- `api2` origin：第二节点服务器的 443 端口。若客户只使用主域名，该域名的证书也必须覆盖 `api2` origin 的 Host；若同时提供备用域名，备用域名也要配置对应证书。
- 健康检查路径：`/readyz`，期望 HTTP 200；不要使用只表示进程存活的 `/health`。共享调度开启后，本节点没有账号或本节点账号权重为 `0` 仍可作为入口；PostgreSQL、Redis、会话 authority 或执行节点就绪检查失败时返回 503。
- 健康检查请求应携带客户实际使用的 Host，并且两个 origin 必须都能在该 Host 下返回有效证书和响应。
- 首次接入先将 `api2` 设为很小的入口权重，确认响应、SSE、WebSocket 和图片链路后再逐步增加。

若使用支持按路径路由和主动健康检查的边缘负载均衡，客户主域名与第二访问域名都使用同一组健康 origin，因此两个地址都可使用同一 Key 并得到相同的鉴权、计费和调度结果。数据面使用可调权重；网页和管理流程使用健康感知的粘性分配，不固定到某个所谓主 origin。公网 origin 权重与 XIASS 节点账号权重相互独立：前者分担客户连接和响应带宽，后者决定新会话使用哪个节点归属账号。若暂时不能使用边缘入口，不建议用普通 DNS 轮询代替，DNS 缓存不能及时摘除故障节点。

使用外部 Caddy 时可参考 `deploy/Caddyfile.multinode.example`。示例对完整模型调用路径做 `5:1` 数据面分流，对网页和管理流程做双节点粘性分配与健康回退。Caddy 的权重只负责公网连接，XIASS 管理端的节点账号权重只负责共享账号池中的新账号选择；两者不要求相同。SSE、WebSocket 等长连接一旦建立，不会被中途搬迁。

入口层应只做一层公网转发；每个 XIASS 节点本地的 Caddy 继续直接反代本机 `127.0.0.1:8080`，不再在两个 XIASS 节点之间叠加入口代理。跨节点只允许 XIASS 为固定账号出口访问一次私网 SOCKS。

## 节点配置

所有对等 XIASS 节点都可使用 `docker-compose.standalone.yml` 连接共享状态层。使用网页配对时，先在已有节点生成一次性邀请码，再在目标节点填写来源地址、邀请码、不同的目标节点 ID 和目标公网地址；来源节点会自动生成目标节点自己的固定出口记录并由目标宿主机 controller 写入 `.env`。手工配置场景下，每个实例的 `.env` 仍必须设置**不同的节点 ID**和该节点自己的默认出口代理 ID；共享数据库中的账号归属与账号代理在所有实例上必须可见且一致。

“默认出口代理 ID”不是客户的 Base URL，也不是入口负载均衡权重。它表示这个应用节点作为账号所属节点时，账号访问上游使用的固定代理/公网出口。最稳妥的生产配置是：每台服务器各准备一个只代表自身公网出口的代理记录，`api` 和 `api2` 使用不同的代理 ID；不要把同一个代理 ID 映射给两个节点。

节点 `api` 示例：

```dotenv
GATEWAY_EXECUTION_NODE_ENABLED=true
GATEWAY_EXECUTION_NODE_ID=api
GATEWAY_EXECUTION_NODE_DEFAULT_PROXY_ID=<api 私网 SOCKS 在共享数据库中的代理 ID>
GATEWAY_EXECUTION_NODE_CONTROL_PLANE=true
GATEWAY_EXECUTION_NODE_LEGACY_UNASSIGNED_NODE_ID=api
GATEWAY_EXECUTION_NODE_LEGACY_UNASSIGNED_PROXY_ID=<api 私网 SOCKS 在共享数据库中的代理 ID>
```

节点 `api2` 示例：

```dotenv
GATEWAY_EXECUTION_NODE_ENABLED=true
GATEWAY_EXECUTION_NODE_ID=api2
GATEWAY_EXECUTION_NODE_DEFAULT_PROXY_ID=<api2 私网 SOCKS 在共享数据库中的代理 ID>
GATEWAY_EXECUTION_NODE_CONTROL_PLANE=false
GATEWAY_EXECUTION_NODE_LEGACY_UNASSIGNED_NODE_ID=api
GATEWAY_EXECUTION_NODE_LEGACY_UNASSIGNED_PROXY_ID=<api 私网 SOCKS 在共享数据库中的代理 ID>
```

配置文件也支持同名字段：

```yaml
gateway:
  execution_node:
    enabled: true
    id: api2
    default_proxy_id: 2
    control_plane: false
    legacy_unassigned_node_id: api
    legacy_unassigned_proxy_id: 1
```

## 网页配对与共享状态

管理端“执行节点”页面提供一次性邀请码配对。**生成邀请码的节点是状态源**；目标节点加入时会接收一次性、AES-GCM 加密且只在 HTTPS 配对响应中传输的运行时加入包，用于切换到状态源的 PostgreSQL、Redis、JWT/TOTP 密钥并启动状态隧道。数据库密码等不会以明文写入配对记录或日志，账号凭据、API Key 和代理凭据不会通过配对复制。

生产就绪必须同时满足：

1. 两台实例运行同一版本和兼容的配对协议。
2. 来源节点拥有完整可用的 PostgreSQL、Redis、JWT 和 TOTP 运行时配置。
3. 目标节点业务数据库为空（仅允许保留安装初始化的管理员和迁移元数据）；有账号、Key、账单、代理或业务分组时必须先单独迁移，不会被静默覆盖。
4. 目标节点的节点 ID 与来源不同，并在网页配对表单填写目标节点的公网 HTTPS 地址。目标机不需要预先手工填写 `GATEWAY_EXECUTION_NODE_*` 或固定出口 ID；来源节点会在共享数据库中为它创建独立的固定出口记录。
5. 目标节点会由宿主机更新控制器备份 `.env`，写入状态源连接参数、目标节点身份和固定出口 ID，启动隧道并只重建目标应用；健康检查和来源确认完成后才显示生产就绪。

如果目标机有业务数据、来源运行时配置不完整、目标应用无法健康启动或来源节点没有收到最终确认，配对会拒绝或自动回滚，页面保持“未生产就绪”。这样可以避免两个独立 XIASS 安装分别扣费，最终造成余额和使用记录分叉。目标机加入后使用来源数据库，不会取得一份可独立接管的数据库副本。来源端 PostgreSQL/Redis 或必经状态隧道不可用时，目标节点也可能无法服务。

配对成功后，两个管理端都连接同一数据库，因此“账号管理”看到的是完整共享账号池。每条账号记录会展示其 `节点` 归属；节点权重、节点心跳和出口映射在“执行节点”页面统一管理。账号编辑/导入不应随意改写系统维护的节点归属；迁移账号到另一节点应通过明确的迁移流程并同步更换对应固定出口。

## 安全启用顺序

### 既有网页登录会话兼容

离线会话迁移 CLI 已移除。多节点启用、网页配对、启动和更新都不会自动迁移会话、重建会话数据或把 Redis 提升为新的状态主节点。

- 未迁移的实例继续使用既有 Redis 会话、签名密钥与原到期时间，不因取消容灾而清空登录状态。
- 已完成 PostgreSQL 会话迁移的实例必须保留 `JWT_REFRESH_TOKEN_STORE=postgres`、数据库中的 authority/transition 记录以及会话、签发和撤销数据。启动 provider 继续校验并读取既有 PostgreSQL 会话；不得改回 Redis、从旧副本补回会话或删除已发布迁移。
- `JWT_REFRESH_TOKEN_MIGRATION_READINESS` 仅为既有配置保留兼容，不是新部署步骤或自动迁移开关。若既有实例仍使用该模式，不应在未核实实际会话 authority 的情况下直接改成 Redis 固定模式。
- 保留已经部署的应用 Redis 凭据、受限 ACL 和部署方已接入的会话运行时环境配置；取消离线迁移工具不意味着可以删除这些文件或恢复旧会话命名空间权限。普通应用不得使用迁移操作员凭据。
- 所有应用节点必须使用与同一份会话 authority 兼容的配置和相同签名密钥；仅修改 `JWT_REFRESH_TOKEN_STORE` 不会导入会话，也不能绕过启动校验。
- 登录、刷新、退出、会话绑定和七天期限继续按既有逻辑执行。备份须包含现有状态和配置，但恢复旧快照可能丢失已确认的撤销记录，不能视作安全的自动回退。

### 应用节点启用

1. 备份共享数据库、Redis、`.env` 和应用数据。
2. 在隔离端口启动每个新实例，分别检查 `/health` 和 `/readyz`，不要接入客户流量。公网入口的健康检查必须使用 `/readyz`。
3. 从每个实例分别测试其本地私网 SOCKS 和对端私网 SOCKS，确认公网出口 IP 符合账号归属。
4. 确认所有实例的数据库、Redis、密钥、版本和时区一致。
5. 全集群只允许一个实例设置 `control_plane=true`，用于启动主动 Token/额度刷新、账号与代理到期扫描、批量图片清理、定时测试、定时备份、渠道监控等不应重复运行的周期任务；其余网关副本设为 `false`。这不会影响任何节点接收客户 API、网页、管理端、Team、OAuth 或请求时 Token 刷新。该任务实例故障且共享状态仍可用时，客户实时请求可由其他健康节点服务；周期维护暂停，不自动选举新的任务领导者，也不产生第二套账务状态。
6. 在“系统设置 -> 网关调度设置”填写全部节点、节点权重和不同的出口代理 ID，再开启“多节点执行负载均衡”。出口代理 ID 必须是共享数据库中的私有代理记录，主节点与第二节点的本地 `default_proxy_id` 必须分别与映射一致。
7. 首次开启会幂等迁移历史未归属账号：归属到历史节点，并且只给原本没有代理的账号补历史出口代理。存在无代理账号、未知节点、账号代理与节点映射不一致时会拒绝开启。
8. 在隔离环境使用独立测试用户、测试 Key 和测试账号验证非流式、SSE、WebSocket、图片、失败切换、粘性、固定出口和单次计费；禁止镜像生产客户请求。先验证两节点健康时账号只走归属出口，再模拟一个测试账号出口不可用，验证重试选择其他健康账号且使用所选账号自己的固定出口；不可迁移会话链不得跨账号重放，无可用账号时应返回失败。
9. 最后才把新实例加入公网健康检查入口，先使用小权重观察，再逐步增加。

## 回退

- 先在入口负载均衡中把故障应用实例的 origin 权重设为 `0` 或摘除，不需要中断其他实例。
- 应用内把对应节点账号权重设为 `0`，停止新会话进入该节点归属账号；这不会自动摘除该应用入口。
- 不删除共享数据库、Redis、账号代理或数据卷。
- 修复后先在隔离端口验证，再恢复小权重。

多节点状态共享时禁止同时运行不同数据库迁移版本，也禁止使用 `docker compose down -v`。

## 故障边界

XIASS 当前没有内置整机自动容灾、Witness 仲裁、Redis Sentinel 自动发现、数据库自动升主或跨节点临时出口接管。执行节点心跳不是数据库接管、管理权限仲裁或状态恢复机制。

必须区分应用故障与整机故障：共享状态和必经隧道仍在线时，健康应用可以继续服务；唯一状态源整机断电时，其他应用节点不能独立接管。外部入口和状态服务的可用性由部署方独立维护，本功能不配置或保证它们的自动恢复。不要停止生产服务来验证这些边界。

- 单个 XIASS 应用节点断联且共享状态仍可用：入口在健康检查失败后摘除该 origin，新请求进入另一健康节点。账号仍使用其归属节点的固定出口；该出口也不可用时，按既有重试规则选择另一个健康账号，不将原账号临时转到本机出口。
- 单个账号出口断联：只影响当前请求并触发账号故障转移，不会因一次网络波动把账号持久停调；网络恢复后下一次请求可以再次选择它。
- PostgreSQL、Redis 或状态隧道不可用：`/readyz` 检查失败时返回 503，外部健康检查入口应摘除未就绪实例；状态连接恢复并通过检查后才恢复接流。XIASS 不会为此复制数据、提升副本或清空会话。
- 公网入口本身断联：单台 Caddy 不能解决自身故障。生产环境需使用托管全局负载均衡，或至少两个独立入口共同指向同一组 XIASS origins。
- 已经送达上游的流式或 POST 请求不会在另一个应用节点透明重放。这样可避免一次请求被上游执行两次并重复产生费用；客户端重新发起的请求继续走正常鉴权、幂等和计费链路。
